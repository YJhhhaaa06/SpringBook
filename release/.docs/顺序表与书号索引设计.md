# 顺序表与书号索引设计

> 代码：`ds/SeqList.java`（有序顺序表）、`book/index/BookMemoryIndex.java`（索引层）、`book/index/BookIndexLoader.java`（启动装载）、`GET /api/books/{id}`、`GET /api/books/isbn/{isbn}`。
> 分工：Trie 回答「以某串开头的书名有哪些」，顺序表回答「这本书是哪一本」。两篇互不替代。

## 0. 结论

1. 一本书一条记录，按 ISBN 升序**连续存放**在顺序表里：二分 O(log n)，下标访问 O(1)。
2. `id → 下标` 用 `HashMap` 做目录，数据只在顺序表里存一份；按 id 取书 O(1)。
3. 索引是**派生视图**：启动时一次全表扫描重建，写路径在事务提交后整行覆盖。
4. 它不是「为了用线性表而用」：详情页、扫码取书、借还校验都走这条读路径，让高频读不再占用连接池和事务；代价是库存字段的同步。

## 1. 这一步解决什么

按 id 取书是详情页、借还、预约校验的共同前置；按 ISBN 取书是扫码枪的入口。两者都是点查。

MySQL 的主键/唯一索引点查本身已是微秒级，所以这个落点**不是**在比「谁查得快」。它换的是另外三件事：

1. **读路径不占连接池**。Hikari 上限 10，详情页与借还校验是最高频的读；走内存后这些请求不再借连接、不开事务。
2. **线性表成为主链路的真实存储**，而不是演示用的样例。`getById` / `getByIsbn` 未命中才回源，日常请求全落在索引上。
3. **热门榜不再回表取书名**。聚合只出 `book_id`，书名与 ISBN 由 `findByIds` 从索引批量取，省掉第三次查询（见《热门榜与TopK设计》§4）。

## 2. 结构

### 2.1 为什么是有序数组，不是链表或哈希表

| 候选 | 查找 | 插入/删除 | 为什么不用 |
|---|---|---|---|
| 有序数组（本方案） | 二分 O(log n) | O(n) 搬移 | 读多写少，搬移可接受；连续内存还能下标访问 |
| 链表 | O(n) | O(1)（已知位置） | 不能随机访问，二分无从谈起；定位本身就要 O(n) |
| 哈希表 | O(1) | O(1) | 能按 ISBN 命中，但拿不到有序序列，且要额外存键；本项目的键就在元素里 |

「有序」买到的是查找：无序表只能线性扫描 O(n)，有序才能二分。付出的只是插入时的搬移，而插入本来就要 O(n)——**没有改变复杂度量级**。

### 2.2 键与元素分离

`SeqList<T, K>` 不要求 `T` 实现 `Comparable`，而是从构造参数接收 `keyOf` 与 `Comparator`：

```java
new SeqList<>(Book::getIsbn, Comparator.naturalOrder())
```

`Book` 是持久化实体，让它为了排序去实现接口，会把存储关注点带进领域模型。键提取器让同一个表也能装别的类型，排序与定位只认键。

### 2.3 复杂度

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `indexOf(key)` | O(log n) | 二分；未命中返回 `-(插入点)-1`，与 `Arrays.binarySearch` 一致 |
| `get(index)` | O(1) | 数组下标 |
| `add(value)` | O(n) | 二分定位 O(log n) + 后缀搬移 O(n) |
| `removeAt(index)` | O(n) | 后缀前移 |
| `set(index, value)` | O(1) | 键不变时同位置替换；键变了直接失败，避免目录错位 |

### 2.4 重建为什么先排序再追加

逐条有序插入的总代价是 O(n²)：每次都要搬移平均 n/2 个元素。`rebuild` 改为先对源数据排序 O(n log n)，再尾部追加 O(1) 并一次性建目录 O(n)。数据量上万时，这是几十毫秒与几秒的差距。

## 3. 索引层 `BookMemoryIndex`

```
SeqList<Book, String>  ← 唯一一份数据，按 ISBN 升序
Map<Long, Integer>     ← id → 下标，只是目录页
```

- **目录不是第二份数据**：`indexById` 只存下标，书名、ISBN、库存都只在 `SeqList` 里。
- **插入/删除要修复后缀下标**：元素搬移后，受影响元素的下标整体位移，`repairIndexFrom` 从落点重写到表尾，与搬移同阶，都是 O(n)。
- **读写锁**：读多写少，读锁可并发；重建整段持写锁，读请求短暂阻塞，而不是读到半成品。
- **按 id 批量取书**：`findByIds` 逐个查目录再取元素，O(k)，供热门榜使用。

## 4. 一致性：缓存了库存，怎么保证不脏

| 决策 | 做法 | 理由 |
|---|---|---|
| 数据来源 | 启动时 `listAll()` 一次，同时灌顺序表与 Trie | 索引可丢弃，重启即对齐；不需要持久化与版本管理 |
| 写路径同步 | 新增、改书名/价格、入库下架、删除、借书、还书、预约流转，全部 `afterCommit` 同步 | 事务回滚时索引不能被改 |
| 同步方式 | **回查整行覆盖**，不按差值加减 | 归还的净变化可能是 0（+1 后被 READY 预约占掉 -1）；借书可能先清理过期预约 +1、再扣减 -1。只有数据库知道是哪一种 |
| 未命中 | 回源查询，**不回填** | 回填会与「删除后 afterCommit 移除」形成竞态，让已删除的书重新出现 |
| 库存字段 | 进索引，但索引**从不参与写入决策** | 扣减、行锁、CHECK 约束都在数据库；索引只服务读 |

`updateTitleAndPrice` 只动书名和价格，ISBN 在业务上不可修改，所以常规更新是同位置替换；万一 ISBN 变了，退化为「摘旧 + 挂新」，靠重新二分定位，不会留下错位条目。

## 5. 接口与前端

- `GET /api/books/{id}`：命中索引 O(1)，未命中回源；不存在 → `40401`。
- `GET /api/books/isbn/{isbn}`：先按原样二分；未命中再把连字符去掉重试一次——扫码枪输出纯数字，库里存的是带连字符的展示格式。
- 联想与热门榜都只读索引，不额外回表。

## 6. 实测

单机、单进程、每项 200 轮，干净种子库（46 本图书 / 14 条借阅 / 2 条预约）。`avg` 受 GC 与 HTTP 抖动影响，`p50` 更能代表常态：

| 接口 | avg | p50 | p95 |
|---|---|---|---|
| `books/{id}`（索引命中） | 7.2 ms | 2.2 ms | 24.3 ms |
| `books/isbn/{isbn}`（二分命中） | 7.7 ms | 2.2 ms | 24.0 ms |
| 对照：`books?keyword=算`（模糊检索） | 12.0 ms | 5.4 ms | 31.0 ms |

**诚实的边界**：46 本书的规模下，数据库点查本身也很快，上表的差距主要来自「少一次连接 + 少一次事务」，不是算法层面的数量级胜利。这个落点的价值在于**主链路真的在用**，以及数据量涨上去后读路径仍然不碰数据库；如果只是偶尔查一次详情，直接查库更省事。

## 7. 明确不做

| 不做 | 原因 |
|---|---|
| 索引持久化 | 派生数据，重启重建即可；持久化只会引入版本与损坏问题 |
| 分布式共享 | 单进程内存索引，多实例会各自持有副本，一致性成本不成比例 |
| LRU / 淘汰 | 存的是图书全集，不是热点子集；淘汰会让「未命中」变成常态 |
| 写穿透 / 写回 | 写仍然走数据库，索引只读；反过来做等于自造一致性问题 |
| 按书号范围查询 | 业务没有这个需求；有序表只是二分的副产品 |

## 8. 验证

- `SeqListTest`（纯单元测试，不启 Spring）：乱序插入后有序、重复键保持插入序、二分命中与未命中约定、同键替换、键变化快速失败、删除后后缀前移、扩容、越界、clear。
- `BookMemoryIndexIntegrationTest`（真库 + Flyway）：ISBN 命中返回整行、改名后两个入口都可见、删除后条目消失、未知 ISBN 返回 404、借还之后缓存库存与数据库一致。
