# 05 排错

按你看到的报错找对应条目。找不到就带上完整日志再问。

## MySQL 5.7 或 MariaDB

**现象一**：建表时失败，日志里出现

```
Unknown collation: 'utf8mb4_0900_ai_ci'
```

**现象二**：连接就被拒绝，报 `Communications link failure`。

**原因**：`utf8mb4_0900_ai_ci` 是 MySQL 8 才有的排序规则；MariaDB 没有它，MySQL 5.7 也没有。另外驱动 `mysql-connector-j 9.7.0` 官方只支持 8.0+。

**处理**：装一个 MySQL 8.4，端口设成 3307 与旧库共存，然后改 `application.properties` 里的端口。不要试图换驱动或改建表语句来解决——那会破坏迁移历史，代价比装一个新库大得多。

确认版本：

```sql
SELECT VERSION();
```

## Java not found

**现象**：双击 `启动.bat` 后窗口一闪而过，或者提示

```
[ERROR] Java not found.
```

**原因**：`PATH` 里没有 `java`，`JAVA_HOME` 也没指向有效的 JDK。

**处理**：

1. 新开一个命令行，执行 `java -version`，确认能看到 21 以上。
2. 看不到就装 JDK 21（<https://adoptium.net/>），安装时勾选"设置 JAVA_HOME"。
3. 装完**重新打开**命令行或资源管理器，环境变量才会生效。

脚本已经做了兜底：`PATH` 找不到时会再尝试 `%JAVA_HOME%\bin\java.exe`，两条都不行才报错。

## UnsupportedClassVersionError

**现象**：

```
java.lang.UnsupportedClassVersionError: ... has been compiled by a more recent
version of the Java Runtime (class file version 65.0), this version ... recognizes
only class file versions up to 61.0
```

**原因**：JDK 版本低于 21。`65.0` 对应 Java 21，`61.0` 对应 Java 17。

**处理**：换 JDK 21+。用 `java -version` 确认当前生效的是哪个。

## Port 8080 was already in use

**现象**：

```
Web server failed to start. Port 8080 was already in use.
```

**处理**（任选其一）：

改端口——`application.properties` 加一行 `server.port=8081`。

或找出占用进程：

**Windows**

```powershell
netstat -ano | findstr :8080
taskkill /PID <上一步的PID> /F
```

**Linux / macOS**

```bash
lsof -i :8080
kill -9 <PID>
```

## Communications link failure

**现象**：

```
Communications link failure
The last packet sent successfully to the server was 0 milliseconds ago.
```

**原因**：连不上数据库。常见三种：MySQL 没启动、端口填错、容器没起来。

**处理**：

1. 确认数据库在跑：

   ```bash
   docker ps | grep mysql        # Docker 方式
   mysqladmin -uroot -p ping     # 本机安装方式
   ```

2. 确认端口。本机安装的 MySQL 默认 **3306**；项目 compose 起的容器映射到 **3307**。`application.properties` 里填错一个数字就会报这个错。

3. 容器刚启动需要十几秒才可用，稍等再试。

## Access denied for user

**现象**：

```
Access denied for user 'root'@'localhost' (using password: YES)
```

**原因**：`application.properties` 里的账号或密码不对。

**处理**：用命令行验证同一组凭据：

```bash
mysql -h 127.0.0.1 -P 3306 -u root -p
```

能登进去说明凭据没问题，检查配置文件里有没有多余空格或引号。

## Unknown database

**现象**：

```
Unknown database 'springbook'
```

**原因**：库不存在，且连接串没带 `createDatabaseIfNotExist=true`。

**处理**：在连接串末尾补上这个参数，或手工建库：

```sql
CREATE DATABASE springbook DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

## Validate failed: checksum mismatch

**现象**：

```
Validate failed: Migration checksum mismatch for migration version 3
```

**原因**：数据库里记录的迁移脚本校验和，与 jar 里的脚本对不上。通常是导入过旧备份，或改过 `db/migration/` 下的 SQL 文件。

**处理**（开发环境）：

```sql
DELETE FROM flyway_schema_history WHERE version = '3';
```

重启后 V3 会重新执行。如果改的是 V1 / V2，就不要随便删记录了——那意味着表结构已经变化，正确做法是重建库。

## Found non-empty schema but no schema history table

**现象**：

```
Found non-empty schema(s) "springbook" but no schema history table.
Use baseline() or set baselineOnMigrate to true to initialize the schema history table.
```

**原因**：库里已经有表，但没有 Flyway 的历史表。典型场景是只导了表结构和数据、没导 `flyway_schema_history`。

**处理**：这种库不能直接用。要么清空重建（删库让 Flyway 从零开始），要么用包含 `flyway_schema_history` 的完整备份还原。

## 页面白屏或 404

**处理**：

1. 确认访问的是 `http://localhost:8080/`，不是 `/index.html` 之外的路径。
2. 确认启动的是本项目的 jar。验证静态资源：

   ```bash
   curl -I http://localhost:8080/js/app.js
   ```

   返回 `200` 说明前端在 jar 里；返回 `404` 说明跑错了程序。

3. 打开浏览器控制台看 `Network`，若是接口 401，说明登录态过期，重新登录。

## 中文乱码

**现象**：页面正常，但命令行日志里的中文是乱码。

**原因**：Windows 终端默认代码页是 GBK。

**处理**：

```powershell
chcp 65001
```

`启动.bat` 已经内置了这条命令，一般不会遇到。

## 时间差 8 小时

**原因**：数据库或 JVM 用了 UTC。连接串里已经指定 `serverTimezone=Asia/Shanghai`，容器也配了 `TZ=Asia/Shanghai`。

**处理**：部署到 UTC 环境时，启动参数加 `-Duser.timezone=Asia/Shanghai`。

## 健康检查是 DOWN

```bash
curl http://localhost:8080/actuator/health
```

返回 `{"status":"DOWN"}` 且日志里有 `Connection refused`，说明数据库没连上，按上面的 [Communications link failure](#communications-link-failure) 处理。

## 启动很慢或卡住

首次启动要执行迁移、灌入演示数据、重建图书内存索引，几秒钟是正常的。卡在

```
HikariPool-1 - Starting...
```

超过十几秒，基本是在等数据库连接超时，检查数据库是否真的可达。
