# 04 数据库与种子数据

## 库表是谁建的

不需要手工建库建表。应用启动时由 **Flyway** 按顺序执行 `src/main/resources/db/migration/` 下的脚本：

| 脚本 | 作用 |
|---|---|
| `V1__init.sql` | 建 5 张表：图书、读者、账号、借阅、预约 |
| `V2__loan_fine_status.sql` | 借阅表增加罚款状态字段 |
| `V3__demo_seed.sql` | 灌入演示数据（仅在借阅表为空时执行） |

执行记录写在 `flyway_schema_history` 表里，重复启动不会重复执行。

库本身由连接串里的 `createDatabaseIfNotExist=true` 自动创建，字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`。

## 为什么日期是相对的

种子数据用 `DATE_SUB(NOW(), INTERVAL 5 DAY)` 生成借出时间，而不是写死某个日期。

写死日期的种子放几周后，所有在借记录都会变成逾期，演示时打开就是一片"逾期 N 天"，看不出正常借阅长什么样。用相对时间后，无论何时第一次启动，四种状态都是齐全的。

需要注意：迁移只执行一次，所以数据在**第一次启动那一刻**定格。过一个月再看，那条"即将到期"的会变成逾期，这是真实系统的正常表现。

## 重置演示数据

借阅被改乱了想恢复初始状态，执行三步：

1. 清掉借阅与预约：

   ```sql
   DELETE FROM loans;
   DELETE FROM reservations;
   ```

2. 删掉 V3 的执行记录（**这一步不能省**）：

   ```sql
   DELETE FROM flyway_schema_history WHERE version = '3';
   ```

3. 重启应用。V3 会重新执行，按当前时间生成一批新数据。

用 Docker 起的数据库，可以直接：

```bash
docker exec -it springbook-mysql mysql -uroot -proot springbook \
  -e "DELETE FROM loans; DELETE FROM reservations; DELETE FROM flyway_schema_history WHERE version='3';"
```

只删业务数据、不删 `flyway_schema_history` 里的记录是没用的，Flyway 认为 V3 已经执行过，不会再跑。

## 为什么不要手工导入 SQL 备份

Flyway 启动时会校验每个迁移脚本的校验和。如果数据库里的 `flyway_schema_history` 与 jar 里的脚本对不上，启动会直接失败：

```
Validate failed: Migration checksum mismatch for migration version 3
```

常见的出错方式：

- 导入了一份旧的整库备份，里面的校验和是旧版本的；
- 只导了表结构和数据，没导 `flyway_schema_history`，Flyway 认为"schema 非空但没有历史表"，同样报错。

所以分发包里不放 SQL 备份。表结构唯一来源就是 Flyway，演示数据由 V3 负责。

需要整库备份时，用 `mysqldump` 导出并**连同 `flyway_schema_history` 一起**，且只在同一版本的 jar 上还原：

```bash
mysqldump -uroot -p --databases springbook --single-transaction > springbook-backup.sql
```

## 表结构速查

| 表 | 说明 | 关键约束 |
|---|---|---|
| `books` | 图书 | ISBN 唯一；可借数 ≤ 总册数 |
| `readers` | 借阅人 | 手机号唯一 |
| `accounts` | 登录账号 | 用户名唯一；一个读者一个账号 |
| `loans` | 借阅记录 | 逾期由 `due_at` 派生，不单独存字段 |
| `reservations` | 预约队列 | 按 `created_at` 先进先出 |

金额一律以「分」为单位存整数，避免浮点误差。借期 30 天、罚款 0.5 元/天、预约保留 48 小时、单人最多在借 5 本，这些参数在 `application.yaml` 的 `book.*` 下。
