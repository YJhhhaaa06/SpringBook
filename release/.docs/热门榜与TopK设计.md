# 热门榜（top-K）设计与落地

> 代码：`ds/MinHeap.java`（有界最小堆）、`ds/TopK.java`（选择器）、`book/service/BookHotService.java`（归并 + 打分）、`GET /api/books/hot`、前端 `views/books.js` 热门榜。
> 定位：三个数据结构落点之一。前缀联想见《书名前缀联想（Trie）设计与落地》，按 ISBN 取书见《顺序表与书号索引设计》。

## 0. 结论

1. 热度 = **借阅次数 + 预约人数 × 2**，默认统计近 30 天。
2. 两条聚合各自 `ORDER BY book_id` 返回，应用侧**双指针归并**成一条有序候选流，再喂给**容量为 k 的最小堆**取前 k。
3. 额外内存 O(k)、时间 O((M₁+M₂)·log k)，不物化整个候选集。
4. 排序口径（权重、时间窗）留在 Java 里：改一行就能调，也能被单元测试直接盯住；书名与 ISBN 由内存索引批量取，不第三次回表。

## 1. 两个实现决策

### 1.1 为什么是两条 SQL，而不是一条

也能写成一条 `UNION ALL` 子查询 + 外层 `GROUP BY SUM(...)`，但那样：

- 时间窗参数要写两遍（借阅一侧带条件、预约一侧不带）；
- 权重 `预约 × 2` 被埋进 SQL 字符串，改权重等于改 SQL，测不到；
- review 时看到的是一坨嵌套子查询，说不清「为什么是 2 倍」。

现在两条聚合各自归属自己的模块（`loans` 归 loan 模块、`reservations` 归 reservation 模块），合并与打分在 `BookHotService` 里，单测直接覆盖。

### 1.2 为什么 `ORDER BY book_id` 而不是 `ORDER BY COUNT(*) DESC`

这是能让数据库少干活的一步。当前种子库（46 本图书 / 14 条借阅 / 2 条活跃预约）的 `EXPLAIN`：

| 查询 | type | 用到的索引 | 扫描行数 | Extra |
|---|---|---|---|---|
| `... FROM loans WHERE borrowed_at >= ? GROUP BY book_id ORDER BY book_id` | `index` | `idx_loans_book_due` | 14 | `Using where` |
| `... FROM reservations WHERE status IN ('WAITING','READY') GROUP BY book_id ORDER BY book_id` | `index` | `idx_res_queue` | 2 | `Using where; Using index` |
| 对照：`ORDER BY COUNT(*) DESC` | `index` | 同上 | 14 | **`Using temporary; Using filesort`** |

按 `book_id` 排序时，`GROUP BY` 顺着索引顺序输出，临时表与 filesort 都消失了；排序这件事被挪到应用侧，而应用侧只需要排 k 条。

代价是应用侧必须自己合并两条有序流——这正是 §1.3 与 §2.2 要做的事。

### 1.3 为什么归并，而不是先塞进 Map 合并

用 `Map<bookId, 计数>` 合并当然更短，但那是 O(M) 个条目的字典，合并完还要再遍历一次打分。两条流都已按 `bookId` 升序，双指针一遍扫完即可：时间 O(M₁+M₂)，除结果流外不产生中间集合。

## 2. 结构

### 2.1 `MinHeap`：为什么是「有界」的堆

普通堆的 `offer` 永远成功；这里的核心语义是**装不下就淘汰最小的那个**，所以 `offer` 的返回值是「是否入选」，而不是「是否入队成功」。

这正是不实现 `java.util.Queue` 的原因：`Queue` 的契约是「能一直放」，和淘汰策略冲突；两者混在一起，调用方看返回值根本不知道在问什么。

复杂度：`offer` / `poll` 为 O(log n)，`peek` 为 O(1)，容量 k 时内存恒为 O(k)。

### 2.2 `TopK.select`

契约一句话：**比较器表示「谁更大」，返回按该比较器降序的前 k 个。**
实现是「容量 k 的最小堆 + `drainAscending().reversed()`」，时间 O(n·log k)，只遍历候选一次。

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `TopK.select(n 个候选, k)` | O(n·log k) | 额外内存 O(k) |
| 对照：`合并 List + sort` | O(M·log M) | 额外内存 O(M)，且产出一份完整排序结果 |

## 3. 比较器方向：一个必须写死的约定

`TopK` 把「谁更大」完全交给比较器，自己只负责「取最大的 k 个并降序输出」。因此 `HOT_ORDER` 的语义必须是**谁更热**，而不是「谁应该排在前面」——后者是输出顺序，与比较器的方向相反。

同分规则也受这个约定约束：热度相同时借阅次数多的优先，仍相同则 `id` 小的优先。但比较器表达的是「更大」，所以 `id` 要用 `reversed()` 参与比较；否则 tie-break 的方向会与整体方向相反，同分条目的顺序在每次请求之间抖动。

把方向固定在一处的好处是：调用方只需回答「谁更热」，容器负责「怎么排」。两处各自翻转一次，结果就会倒过来——这是契约问题，不是排序算法问题。

## 4. 一致性：这个落点没有自己的状态

热门榜**不维护任何内存榜单**：每次请求都从 `loans` / `reservations` 现算两条聚合。因此不存在快照过期、增量维护、重启重建这些问题——借还一旦提交，下一次请求立刻反映。

书名与 ISBN 来自 `BookMemoryIndex`（派生视图，写事务提交后同步），热门榜只读 `id/isbn/title`，不参与写决策；索引里没有的 id（历史残留）直接跳过，不让整榜失败。

代价是每次请求**两条聚合查询**；相比「一条 UNION ALL」多一次往返，换来的是权重与时间窗留在 Java、可被单测覆盖。见 §6。

## 5. 接口与前端

`GET /api/books/hot?limit=&days=`

- `limit` 默认 8、上限 30；`days` 默认 30，`0` 表示不限时间窗。
- 返回 `{ id, isbn, title, borrowCount, reservationCount, score }` —— 把 `score` 一并返回，是为了让前端能解释「为什么它排在这里」，而不只是给一个名次。

前端把榜单做成「检索框下方的一排胶囊」：点击条目把书名填进搜索框并检索，不做第二套详情页。榜单与检索并行请求，且榜单单独 `catch` 兜底——它是附加信息，挂了不该让整页检索变成错误页。

## 6. 实测

单机、单进程、每项 200 轮，干净种子库（46 本图书 / 14 条借阅 / 2 条活跃预约）。`avg` 受 GC 与 HTTP 抖动影响，`p50` 更能代表常态：

| 接口 | avg | p50 | p95 |
|---|---|---|---|
| `hot?limit=5` | 11.3 ms | 4.8 ms | 29.7 ms |
| `hot?limit=20&days=0` | 10.4 ms | 4.5 ms | 28.3 ms |
| 对照：`books?keyword=算`（单条检索） | 12.0 ms | 5.4 ms | 31.0 ms |

**诚实的结论**：

1. 热门榜与分页检索在**同一量级**（p50 4.8 ms vs 5.4 ms）：它只有两条聚合查询，书名/ISBN 走内存索引，没有第三次回表。首页一次展示、20 ms 内可接受，但它不适合做成逐键请求。
2. **堆在这里的贡献无法被测出来**：候选只有 14 本有借阅、2 本有排队。写堆不是为了这 14 条，而是为了把上界钉住：候选涨到十万级时仍是 O(k) 内存 + O(M·log k)，而「合并 List 再 sort」要物化整份结果。
3. 如果哪天真的嫌 20 ms 慢，正确的下一步是**把两条聚合合成一条**或加缓存，而不是换排序算法——瓶颈在查询次数，不在排序。

## 7. 明确不做

| 不做 | 原因 |
|---|---|
| 热度快照表 / 增量维护 | 会引入「排行榜与借还不同步」的一致性问题，当前没有规模压力 |
| 按小时窗口、时间衰减 | 业务口径没定，加了只是猜 |
| 分页 | 榜单的语义就是「前 k 名」，翻页没有意义 |
| 作者/分类维度 | `books` 表没有这些字段 |

## 8. 三个落点的分工

| | 书名前缀联想（Trie） | 书号索引（顺序表） | 热门榜（有界堆） |
|---|---|---|---|
| 结构 | 字符前缀树 | 有序数组 + 二分 | 有界最小堆 + 双指针归并 |
| 解决什么 | 逐键前缀查询 | 按 id / ISBN 点查 | 取热度前 k |
| 是否必需 | 否：前缀 SQL 本来能走 range 索引 | 否：唯一索引点查本身已经很快 | 否：`List + sort` 也能出正确结果 |
| 真实收益 | 逐键查询不碰数据库 | 读路径不占连接池与事务 | 不物化候选集；把 filesort 从数据库挪到应用侧只排 k 条 |
| 引入的成本 | 内存索引的一致性维护 | 库存字段的提交后同步 | 两条聚合查询 |
| 共同点 | **都是「结构正确、收益随规模放大」，不是当下的性能救火** | 同左 | 同左 |

三者都不承诺「性能提升 X 倍」：在当前数据量下，直接 SQL 也能工作。价值在于把复杂度上界钉住，并且这条路径真的被主链路调用。
