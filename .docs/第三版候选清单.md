# 第三版候选清单（交接材料）

> **状态更新（2026-10-20）**：本清单的结论已落地为前端版本，设计、取舍与验收见 `.docs/第三版实施方案.md`。
> 未做项（读者注销、缓存、登录锁定等）已在实施方案 §一、§八 记录理由。

> 写给下一轮迭代的 agent：本文档是范围讨论的结论，非实施方案。动手前先读 `.docs/原始需求.md`、`.docs/技术选型.md`、`.docs/接口文档.md`（v2，21 接口 + 错误码表）。
> 现状（2026-10-19）：第二版已完成，58 集成测试 + 30 步冒烟全绿，提交 13c6077。

## 一、结论先行

1. **当前已是功能完备的可用版本**（对 API 消费者而言）：原始需求 + 两个扩展全部闭环，且补齐了罚款缴纳、借阅上限、数据归属、自助注册、入库下架。
2. **下一版做前端，不做缓存**。
   - 缓存：单机 MySQL + 行锁 + 索引，数据规模撑几年没问题，是过早优化；且图书库存是强一致数据（available_copies 被条件更新+行锁保护），引入缓存反而制造一致性 bug。离线约束下 Redis 依赖也要先盘点。**除非未来有真实规模压力，否则不做**。
   - 前端：真正的可用性缺口。纯 REST + curl 的"可用"只对开发者成立，图书馆实际使用者（管理员/读者）需要界面。做前端能让项目从"演示"变"可交付"。

## 二、前端迭代的方案约束（建议）

- 轻量优先：静态 HTML+JS 或单个 SPA（Vue/React 皆可），直接调现有 REST，**不改后端接口**。
- 需要的少量后端配套：CORS 配置（若前后端分离部署）；其余接口已够用。
- 登录态：token 存 localStorage/sessionStorage，401 统一跳登录页（token 2h 过期）。
- 错误码 → 中文提示映射：直接复用接口文档 §7 错误码表；`40001` 的 data 是字段级明细，可做表单内联报错。
- 金额：出参同时有 `*Cents`（分）与换算好的 `*`（元），展示用元字段，计算用分。

## 三、围绕原始需求的边界情况（做前端时顺手处理或明确不做）

| # | 事项 | 判断 |
|---|---|---|
| 1 | 读者注销/删除接口缺失（退卡场景），需带保护：有在借/待缴罚款/活跃预约则拒绝 | 建议做（后端一个小接口 + 前端按钮） |
| 2 | 无登录失败锁定：admin 口令可被暴力尝试 | 课程级接受，记录不做；如做，账户表加 fail_count + 锁定时间 |
| 3 | 无登出/改密后旧 token 失效：无状态 JWT 固有代价 | 已记录，不做（黑名单/版本号是过度设计） |
| 4 | phone 只校验长度无格式正则；username 无字符集限制 | 前端做格式提示即可，后端从简 |
| 5 | 时间用服务器本地时区（Asia/Shanghai 显式配置）：部署到 UTC 环境会偏 8 小时 | 部署文档注明即可，不改代码 |
| 6 | READY 保留期（holdUntil）到点前读者可取书：前端应展示倒计时 | 前端事项 |
| 7 | 40912 版本冲突：前端提示"数据已被他人修改，请刷新重试" | 前端事项 |
| 8 | 下架后图书仍会被历史借阅记录引用（join 查询带书名）→ 前端书名展示无需特判 | 已天然支持 |
| 9 | priceCents 为 INT（约 21 万元/册上限）、罚款封顶书价已覆盖极端逾期 | 无需处理 |

## 四、下一版明确不做

- 缓存/Redis（理由见上）
- 定时任务替代惰性清理（现方案已验证）
- 图书扩展字段（作者/分类/封面）、消息通知、多馆/分库

## 五、验收口径建议（前端版）

- 前端能走通：登录/注册 → 图书检索 → 借书 → 预约 → 归还 → 罚款缴纳（管理员）→ 读者管理（管理员）
- 后端测试保持全绿（58），不改接口契约；如新增读者注销接口，补集成测试并更新接口文档
