# 书名前缀联想（Trie）设计与落地

> 状态：**已落地**（2026-10-21），全量测试 75/75 绿、前端验收 25 项 0 失败。
> 代码：`ds/CharTrie.java`（结构本体）、`book/index/BookIndex.java`（索引与一致性）、`book/index/BookIndexLoader.java`（启动装载）、`BookService.suggest`、`GET /api/books/suggest`、前端 `views/books.js` 下拉。
> 定位：数据结构进业务的第一个落点。本文的重点不是"我实现了 Trie"，而是**为什么这里需要它、它在哪些前提下不值得**。

## 0. 结论

1. 用一个泛型字符 Trie 存书名，前缀检索代价 O(L·log σ + m)，与全表规模无关。
2. 索引是**派生视图**：权威数据仍在 MySQL，启动全量重建 + 写事务提交后增量同步，因此可以被随意丢弃、任意重启。
3. 联想只返回 `id / isbn / title`，**不回查数据库**，也不会返回会过期的库存数字。
4. 除 Trie 之外没有自研第二个结构：子节点表、id→键的字典、并发锁全部用 JDK。**不为了实现而实现**。

## 1. 这一步解决了什么，又没解决什么

### 1.1 现有查询的真实代价（EXPLAIN 实测）

| 查询 | type | 用到的索引 | 扫描行数 |
|---|---|---|---|
| `title LIKE '%算%'`（**现有检索**） | `index` 全索引扫描 | `idx_books_title` | 18 |
| `title LIKE '算%'`（假如新加前缀查询） | `range` | `idx_books_title` | 1 |
| `isbn LIKE '978-7-111%'` | `range` | `uk_books_isbn` | 3 |

**必须说清的一点**：前缀查询在 MySQL 里本来就能走 range 索引。所以"Trie 避免了全表扫描"这句话只对**现有的 `%kw%` 包含匹配**成立；如果只是"再加一个前缀接口"，直接写 SQL 也是 range 扫描，Trie 并不是必需。

### 1.2 那它换来了什么（三条真实收益）

1. **逐键零往返**。联想是"每敲一个字都要问一次"的接口，走 SQL 时每次都要占用连接池（本项目 Hikari 上限 10）。内存索引走进程内读锁，把这类高频短查询从数据库连接这个稀缺资源上挪走。
2. **不需要排序与回表**。结果按书名字典序直接产出（子节点 `TreeMap` + DFS，凑够 limit 立刻收手）；SQL 版要 `ORDER BY title` 再回表取 `isbn`。
3. **结果字段天然无易变值**。只吐 `id/isbn/title`，既不用 JOIN 库存，也不会出现"下拉里的可借数已经过期"的问题。

### 1.3 诚实的边界：当前规模下它不是必需品

本机、单进程、每项 200 轮的实测（18 条图书）：

| 接口 | avg | p50 | p95 |
|---|---|---|---|
| `suggest?q=算` | 3.3 ms | 1.9 ms | 16.2 ms |
| `suggest?q=深` | 1.7 ms | 1.2 ms | 2.4 ms |
| `books?keyword=算`（`%算%`） | 5.9 ms | 4.0 ms | 22.0 ms |

差距主要来自 HTTP 与 JSON 序列化，不是算法。**万级以下的数据量，这条 Trie 不是性能必需品**；它换来的是"逐键高频查询不碰数据库"，代价是"多维护一份内存索引的一致性"。是否值得，取决于是否真的出现"并发输入用户数 × 书目规模"的压力；否则给 `title` 加个前缀查询、让 SQL 走 range 索引更省事。

本项目引入它的判断是：这是一份数据结构作业，需要一个**真实被调用、能被数据验证**的落点；同时它的代价（一致性维护）是可控且可解释的，不像"为了用堆而写堆"那样只有装饰性。

## 2. 结构设计

### 2.1 `CharTrie<V>`：只做前缀检索

**为什么不实现 `java.util` 的 `Collection / List / Map`**：Trie 没有下标访问、没有"遍历全部元素并按位置修改"的语义，硬套接口会得到一堆语义不成立的方法（`subList` 该怎么切？`get(3)` 是什么？）。它借用的是迭代器协议以外的东西 —— 只有 `TreeMap` 作为子节点表。

**子节点为什么是 `TreeMap` 而不是数组或手写哈希表**：

- 形状由数据决定，一个字符节点的子节点数通常是个位数，65536 长度的数组不现实；
- 手写开放寻址/链地址在这里的收益为零，却要多承担一轮正确性验证；
- `TreeMap` 换来**按字符有序遍历** —— 这是 `prefixValues` 能"凑够 limit 就停"、且输出顺序稳定的前提。

**一个键可挂多个值**：同一书名可能对应不同 ISBN（本项目真实数据里就有——冒烟测试遗留的同名书），因此终点是一个小桶而不是单值。`size()` 统计的是**键数**，与 `Map.size()` 同义。

**删除要剪枝**：删掉键上最后一个值后，若沿途节点既无值也无子节点，则逐层摘掉，避免删除后残留一条没有终点的长链（否则 `prefixValues` 会走进死胡同）。

### 2.2 复杂度

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `put(key, value)` | O(L·log σ) | L 为键长，σ 为单节点子节点数 |
| `remove(key, value)` | O(L·log σ) | 含向上剪枝 |
| `prefixValues(prefix, limit)` | O(L·log σ + m) | m 为**实际返回条数**，凑够即停 |
| 对照：`LIKE '%kw%'` | O(n) | n 为表行数，无法提前终止 |

### 2.3 哪些地方直接用 JDK

| 位置 | 用了什么 | 为什么不自己写 |
|---|---|---|
| 节点子表 | `TreeMap<Character, Node>` | 需要有序遍历；手写有序哈希表没有收益 |
| 索引的 id→键 | `HashMap<Long, String>` | 改名/删除时定位旧键，纯字典查找 |
| 并发保护 | `ReentrantReadWriteLock` | 读多写极少，读读并行 |
| 返回集合 | `List.copyOf` | 防止调用方改到内部桶，也与容器结构无关 |

## 3. 一致性：引入内存索引的真正成本

这一节比 Trie 本身更重要 —— 内存索引出问题，通常不是结构写错，而是同步时机写错。

| 决策 | 做法 | 理由 |
|---|---|---|
| 数据来源 | `books` 表全量 → `BookIndexLoader`（`ApplicationRunner`） | 索引可丢弃，重启即对齐；不需要持久化与版本管理 |
| 写路径同步 | `create / update / delete` 三处调 `syncAdd / syncUpdate / syncRemove` | 覆盖所有会改书名或存在性的入口 |
| 同步时机 | **事务提交后**（`afterCommit`），不是方法末尾 | 事务回滚时索引不能被改，否则内存里多出一条库里没有的书 |
| 改名 | 先摘旧键再挂新键 | 避免"旧书名还能搜到、新书名搜不到" |
| 调册 `adjustCopies` | **不同步** | 只改册数，不影响书名 |
| 库存 / 预约 / 罚款 | **绝不进索引** | 强一致数据，唯一正确性来源是行锁 + 条件更新；搬进内存等于自造 bug |

联想不返回 `availableCopies` 是同一个思路的延伸：与其缓存一个随时会变的数字，不如让它根本不出现；用户点选后由正常检索接口给出实时库存。

## 4. 接口与前端

`GET /api/books/suggest?q=&limit=`：参数名用 `q` 而非 `keyword`，就是为了让调用方一眼看出它和检索接口的**语义差异**（前缀 vs 包含）。`q` 为空返回空数组，不报错。

前端（`views/books.js`）三个细节：

1. **140ms 防抖**：连续输入只发最后一次请求。
2. **竞态丢弃**：请求带序号，且回包时比对输入框当前值；慢响应不会盖掉新输入的结果。
3. **失焦与点击**：面板的 `mousedown` 先 `preventDefault()`，否则输入框先失焦、下拉先关闭，点击会落空。

## 5. 明确不做

| 不做 | 原因 |
|---|---|
| 拼音 / 首字母联想 | 需要外部词典（汉字→拼音），不是数据结构问题 |
| 作者、分类联想 | `books` 表没有这些字段，加字段属于需求扩张 |
| ISBN 前缀联想 | 唯一索引本来就是 range 扫描（见 §1.1），不需要索引层 |
| 中缀模糊（"法导"命中"算法导论"） | Trie 不擅长，交给现有 `LIKE '%kw%'` |
| 索引持久化 / 分布式共享 | 单机进程内索引，持久化只会引入版本与损坏问题 |
| 联想按热度排序 | 需要借阅统计 + 每次借还重排前缀，复杂度不成比例 |

## 7. 如果要继续加结构

同一个判断标准（现有 SQL 能不能做、差多少、代价是什么）适用于下一步：

| 候选 | 结构 | 需要先回答的问题 |
|---|---|---|
| 热门榜 top-K | 二叉堆 O(n log k) | `ORDER BY count DESC LIMIT k` 在万级数据下是否真的慢？ |
| "借过这本的人也借过" | 邻接表 + BFS（`loans` 天然是读者↔图书二部图） | 两跳 BFS 与一条自连接 SQL 的差距？去重需要哈希集合 |
| 图书详情 LRU | 哈希表 + 双向链表 | 只能缓存静态字段，`availableCopies` 必须实时 |

**先有数据，再决定结构**；没有 benchmark 支撑的结构，在报告里只会变成负分项。
